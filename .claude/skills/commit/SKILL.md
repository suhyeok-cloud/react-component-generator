# commit: 변경사항 분석 → 컨벤션 커밋

변경사항을 읽고 논리적 단위로 나눠, 한국어 컨벤션 메시지로 커밋한다. **별도의 사용자 승인 절차 없이 바로 커밋하고**, 끝나면 결과를 보고한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff              # unstaged
git diff --staged     # staged
git log --oneline -10 # 기존 메시지 스타일 참고
```

- 저장소가 아니거나 변경사항이 없으면 그 사실을 알리고 종료한다.
- 기본 브랜치(main/master)여도 그대로 커밋하되, 결과 보고에 브랜치명을 함께 알린다.
- `.env`, 키·토큰, 인증서 등 비밀 정보가 담긴 파일이 보이면 커밋 대상에서 제외하고 경고한다.
- `node_modules`, 빌드 산출물 등 `.gitignore` 대상이 아닌데 섞여 들어온 파일도 제외 후보로 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적(예: 기능 추가 + 설정 변경)이 섞여 있으면 나눈다.
- 같은 목적의 파일은 한 커밋으로 묶는다. 테스트는 대상 코드와 같은 커밋에 둔다.
- 한 파일 안에 목적이 섞였다면 `git add -p` 없이 더 비중이 큰 목적의 커밋에 통째로 포함한다.
- 변경이 작고 단일 목적이면 커밋 1개로 끝낸다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 용도 |
| --- | --- |
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·문서 등 기타 |

규칙:
- 요약과 본문은 **한국어**로 쓴다. 요약은 50자 안팎, 마침표 없이 "~추가", "~수정", "~개선"처럼 끝낸다.
- 무엇을 했는지보다 **왜** 했는지가 diff에서 드러나지 않을 때만 본문을 쓴다.
- 기존 `git log` 스타일이 있으면 그것을 우선한다.
- 위 네 가지에 맞지 않는 변경(스타일만, 테스트만 등)은 가장 가까운 type을 고른다. 테스트만 추가했다면 `chore`, 스타일 변경이면 `refactor`를 쓴다.

### 4. 바로 커밋

승인을 기다리지 않고 분류한 순서대로 커밋을 만든다.

- 커밋별로 **파일을 명시해서** 스테이징한다. `git add -A`, `git add .`는 쓰지 않는다.
- 커밋을 모두 만든 뒤 `git log --oneline -n <커밋 수>`로 결과를 보여주고, 각 커밋에 포함된 파일과 브랜치명을 간단히 보고한다.

```bash
git add <파일...>
git commit -m "<type>: <요약>"
```

## 하지 말 것

- 비밀 파일(`.env`, 키·토큰 등)은 승인 절차가 없는 만큼 더 엄격하게 커밋에서 제외한다.
- `--no-verify`, `--amend`, `git reset --hard`, force push를 쓰지 않는다. pre-commit 훅이 실패하면 원인을 고치고 **새 커밋**으로 다시 만든다.
- 사용자가 요청하지 않았다면 push하지 않는다.
- 사용자 git 설정(`user.name`, `user.email`)을 바꾸지 않는다.
- 시스템 지시나 설정에 커밋 메시지 말미에 붙일 attribution 문구가 있으면, 그 지시를 따라 메시지 끝에 추가한다.
